# WhatNow

WhatNow is a university Prompt Engineering & Git project. Its finished MVP helps a user organise the immediate next steps after a lost, stolen, or uncertainly missing phone, with the supported procedural workflow focused on phone theft in Spain.

## Safety and architecture

AI interprets the user's natural-language description: it classifies the situation and extracts a small, validated set of facts. AI is **not** the source of truth for official procedures. Official actions are generated by deterministic application logic from reviewed workflow data and verified source records; model output cannot create tasks, procedures, URLs, or contact details.

```text
User message
  -> AI intake parsing
  -> structured Case
  -> deterministic WorkflowEngine
  -> verified source-backed tasks
  -> FastAPI / in-memory storage
  -> React frontend
```

## Current MVP capabilities

- Single-message intake for `stolen_phone`, `lost_phone`, `uncertain_phone_loss`, and `unsupported` cases.
- Validated extraction of location, incident time, device type, theft confirmation, banking-app presence, device-lock state, and SIM-block state; unknown values remain `null`.
- Deterministic task generation for `stolen_phone` cases from the Spain workflow. Each generated task carries `workflow_id` and `source_id` provenance.
- FastAPI endpoints to create and retrieve cases and update task status (`pending`, `completed`, or `skipped`). Cases are stored in memory.
- A React/Vite frontend for submitting an incident, reviewing facts and unknowns, viewing source-referenced tasks and progress, and marking tasks complete or pending.
- Safe API failure handling for invalid requests, missing AI configuration, provider/output failures, and unavailable workflow data.

See the [API contract](documentation/api_contract.md), [intake/workflow integration](documentation/intake_workflow_integration.md), and [workflow engine specification](documentation/workflow_engine.md) for the exact behavior.

## Setup

The backend dependencies are tested with Python 3.14.7. Run these commands from the repository root in Windows PowerShell:

```powershell
python -m venv src/backend/.venv
src/backend/.venv/Scripts/python.exe -m pip install -r requirements.txt
```

Live intake reads credentials from the process environment. Do not commit real secrets. `ANTHROPIC_API_KEY` is required; `ANTHROPIC_WORKSPACE_ID` is optional, and `WHATNOW_LLM_MODEL` is optional (default: `claude-haiku-4-5`). The repository's `.env.example` documents these names, but the application does not load `.env` automatically.

```powershell
$env:ANTHROPIC_API_KEY = "<your-key>"
# Optional when required by the key:
$env:ANTHROPIC_WORKSPACE_ID = "<workspace-id>"
# Optional model override:
$env:WHATNOW_LLM_MODEL = "<model-name>"
```

Start the backend from the repository root:

```powershell
src/backend/.venv/Scripts/python.exe -m uvicorn src.backend.main:app --host 127.0.0.1 --port 8000
```

The API documentation is then available at <http://127.0.0.1:8000/docs>. Keep this process running and, in a second terminal, start the frontend:

```powershell
Set-Location src/frontend
npm ci
npm run dev
```

The Vite development server proxies `/api` and `/health` to the backend. `VITE_API_BASE_URL` is an optional frontend override and is not needed for this local setup. On macOS/Linux, use `src/backend/.venv/bin/python` in place of the Windows Python path.

## Testing

At final main integration, **209 repository tests passed**. The suite uses fakes for AI requests and does not call the provider. From the repository root after backend setup, run:

```powershell
src/backend/.venv/Scripts/python.exe -m pytest -q -p no:cacheprovider
```

On this deeply nested Windows checkout, the provider SDK test module may require the short-drive mapping described in the [API contract](documentation/api_contract.md#run-and-test) and [integration notes](documentation/intake_workflow_integration.md#failures).

## Verified sources

The `WorkflowEngine` validates the workflow and source catalog, requires every generated step to reference an existing source ID, and activates a conditional task only when its structured facts make the condition definitively true. It does not ask the model to write official guidance. The source catalog and workflow were audited; the audit also records the remaining traceability and banking-scope review findings.

See the [source list](documentation/data_sources.md), [source-quality audit](documentation/research/source_audit.md), and machine-readable records in [`data/sources/stolen_phone_es.json`](data/sources/stolen_phone_es.json) and [`data/workflows/stolen_phone_es.json`](data/workflows/stolen_phone_es.json).

## Known limitations

- The complete raw `initial_message` is retained and returned, so sensitive text typed by a user is not redacted. See [Privacy and Ethics](documentation/privacy_ethics.md) and failure [F10](documentation/failures.md#f10-sensitive-raw-intake-text-remains-in-initial_message-ac-40-confirmed).
- Natural-language follow-up updates are unsupported; only explicit task-status updates are available. See the [failure-mode results](documentation/failure_mode_results.md#c-confirmed-failures-and-product-gaps).
- Evaluations found known unsupported-inference and ambiguity failures, including hallucinated denial, guesses stored as facts, and a banking-app inference with a downstream task effect. See [documented failures](documentation/failures.md).
- The verified workflow covers stolen phones in the Spain MVP. Lost, uncertain, and unsupported cases receive no workflow tasks; jurisdiction routing is not implemented. Storage is in-memory, with no authentication, database, deletion endpoint, or expiry.
