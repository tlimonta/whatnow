# WhatNow

WhatNow is a university Prompt Engineering & Git project developed for DAT32-91.

The finished MVP helps a user organise the immediate next steps after a lost, stolen, or uncertainly missing phone, with the supported procedural workflow focused on phone theft in Spain.

The project was designed not only to produce a working prototype, but also to make the development process visible: repository evolution, prompt iterations, Git collaboration, testing, failures, source verification, and technical decisions are all documented in the repository.

## Objective

Unexpected situations such as losing or having a phone stolen can quickly become confusing. A user may need to think about banking apps, SIM blocking, device security, police reporting, personal data, and other actions at the same time.

The objective of WhatNow is to turn an unstructured natural-language description of the situation into a structured case and a clear action plan.

The main architectural principle is:

> AI interprets the situation. Deterministic systems control the trusted actions.

The language model is therefore used for classification and information extraction, but not as the source of truth for official procedures.

## Safety and architecture

AI interprets the user's natural-language description: it classifies the situation and extracts a small, validated set of facts.

AI is **not** the source of truth for official procedures.

Official actions are generated by deterministic application logic from reviewed workflow data and verified source records. Model output cannot directly create tasks, procedures, URLs, or contact details.

```text
User message
    ↓
AI intake parsing
    ↓
Structured Case
    ↓
Deterministic WorkflowEngine
    ↓
Verified source-backed tasks
    ↓
FastAPI / in-memory storage
    ↓
React frontend
```

This separation was chosen because natural-language understanding benefits from an LLM, while official actions require stronger control, traceability and provenance.

  - invalid requests
  - missing AI configuration
  - provider failures

  - unavailable workflow data

## `.gitignore` and repository hygiene

The repository intentionally does not version machine-specific, generated or sensitive files.

Examples include:

```text
.env
.venv/
node_modules/
Python cache files
temporary build files
local editor files
```

Secrets such as API keys must never be committed to Git.

The repository instead versions the files required to recreate the environment, such as:

```text
requirements.txt
package.json
package-lock.json
.env.example
tests/
documentation/
```

The principle is:

> Do not version the local environment. Version the information needed to recreate it.

For example, `node_modules/` is ignored because it can be recreated with `npm ci`, while `package-lock.json` is committed because it helps reproduce the dependency versions used by the project.

## Setup

The backend dependencies were tested with Python 3.14.7.

Run the following commands from the repository root.

### Windows PowerShell

Because deeply nested Windows paths can cause installation problems with packages containing very long filenames, a short virtual-environment path is recommended:

```powershell
py -3.14 -m venv C:\wnvenv
C:\wnvenv\Scripts\python.exe -m pip install -r .\requirements.txt
```

If your checkout path is short enough, a project-local virtual environment can also be used:

```powershell
python -m venv src/backend/.venv
src/backend/.venv/Scripts/python.exe -m pip install -r requirements.txt
```

### Environment variables

Live intake reads credentials from the process environment.

Do not commit real secrets.

`ANTHROPIC_API_KEY` is required.

`ANTHROPIC_WORKSPACE_ID` is optional and may be required depending on the API key configuration.

`WHATNOW_LLM_MODEL` is optional. The project default is:

```text
claude-haiku-4-5
```

The repository's `.env.example` documents the configuration names, but the application does not automatically load `.env`.

Windows PowerShell example:

```powershell
$env:ANTHROPIC_API_KEY = "<your-key>"

# Optional when required by the key:
$env:ANTHROPIC_WORKSPACE_ID = "<workspace-id>"

# Optional model override:
$env:WHATNOW_LLM_MODEL = "<model-name>"
```

## Prompt engineering

Prompt Engineering was treated as an iterative and measurable part of the project rather than as a single final prompt.

Three main prompt versions were evaluated:

```text
V1
 ↓
V2
 ↓
V3
```

### V1

The initial version was intentionally less constrained.

It frequently invented its own schema, used inconsistent field names, represented unknown information with free-text values, and sometimes added additional advice.

### V2

The second version introduced:

- explicit schema constraints
- stronger JSON requirements
- evidence requirements
- explicit handling of unknown values
- restrictions on unsupported inference

This significantly improved structured output and classification.

### V3

The third version strengthened:

- null handling
- ambiguous-case handling
- evidence constraints
- unsupported-inference rules
- separation between interpretation and procedure

The final decision was based on measured results rather than subjective preference.

See [prompt strategy](documentation/prompt_strategy.md) and [evaluation results](documentation/evaluation_results.md).

## AI evaluation

The repository includes both a labelled prompt benchmark and an adversarial system-level evaluation.

### Prompt benchmark

The evaluation used:

```text
40 labelled cases
×
3 prompt versions
=
120 model calls
```

The same cases were tested against V1, V2 and V3.

Measured areas included:

- structured-output validity
- case classification
- field extraction
- missing-field handling
- unsupported inference
- ambiguity handling
- prompt-injection resistance

In the recorded benchmark run, V3 produced:

- 40/40 valid outputs after deterministic parsing
- 40/40 correct case classifications
- 101/102 correct evaluated field extractions
- 6/6 ambiguous cases handled according to the benchmark criteria

These results refer to one recorded evaluation run and should not be interpreted as universal model accuracy.

### Deterministic parser safeguard

One important finding was that all 120 raw model answers were wrapped in Markdown code fences even when the prompt explicitly instructed the model not to use them.

This showed that prompting alone was not sufficient.

The deterministic parser therefore became an important part of the production pipeline.

## Failure-mode testing

The project also includes an adversarial evaluation dataset covering 22 cases.

Categories include:

- prompt injection
- unsupported inference
- sensitive-looking data
- contradiction
- ambiguity
- irrelevant input
- instruction-like text
- multilingual input
- longer input
- unsupported update behavior

The purpose was not to prove that the AI system is perfect, but to identify where it fails and document those limitations.

Confirmed issues include:

- `theft_confirmed=false` sometimes inferred from ordinary loss language even without an explicit denial
- banking-app presence inferred from a bank verification-code mention in one adversarial case
- raw `initial_message` content is still retained
- natural-language follow-up updates are not currently supported

These failures were documented rather than hidden.

## Verified sources

The `WorkflowEngine` validates the workflow and source catalog.

Every generated workflow step must reference an existing source ID.

A conditional task is activated only when its structured facts make the condition definitively true.

The system does not ask the language model to generate official guidance.

The verified source layer was reviewed through a separate source-quality audit.

The audit checked:

- source authority
- source domain
- workflow wording
- source IDs
- conditions
- verification dates

## Main technical choices

### Why FastAPI?

The backend, AI pipeline and evaluation tooling were already Python-based.

FastAPI provided a lightweight way to expose the application through an API while keeping the architecture simple for the MVP.

### Why React and Vite?

The frontend needed an interactive interface for:

- submitting incidents
- reviewing facts
- displaying tasks
- updating progress

React provided reusable UI components, while Vite kept the development and build process lightweight.

### Why an LLM?

Users describe incidents in natural language rather than structured fields.

The LLM is useful for interpreting that unstructured input and turning it into a structured case.

### Why not let the LLM generate the complete procedure?

Official procedures need reliability and traceability.

An LLM may hallucinate or infer unsupported information.

For that reason, trusted actions come from deterministic workflow data rather than generative model output.

### Why JSON workflow data?

Workflow logic and official guidance can be reviewed, tested and updated independently from the prompt.

It also allows every task to retain explicit provenance through a `source_id`.

### Why in-memory storage?

This was an MVP scope decision.

Persistent storage, authentication and account management would be required for a production system, but were not necessary to validate the main architecture during the course.

## Known limitations

- The complete raw `initial_message` is retained and returned, so sensitive text typed by a user is not currently redacted.
- Natural-language follow-up updates are unsupported; only explicit task-status updates are available.
- Evaluations found known unsupported-inference and ambiguity failures.
- The verified procedural workflow currently focuses on stolen phones in Spain.
- Lost, uncertain and unsupported cases receive no workflow tasks.
- Jurisdiction routing is not implemented.
- Storage is in memory.
- There is no authentication system.
- There is no persistent database.
- There is no deletion endpoint.
- There is no automatic expiry or retention policy implementation.

## Main challenges and lessons learned

### Prompt instructions are not guarantees

Even explicit formatting instructions were sometimes ignored by the model.

This led to stronger deterministic parsing and validation.

### Unknown information should remain unknown

One recurring challenge was preventing the model from converting uncertainty into a definite fact.

This motivated stricter null handling, evidence rules and adversarial testing.

### Official sources still require interpretation

Using an official source does not automatically mean that every statement in a workflow is fully supported by that source.

The source audit identified cases where the wording or traceability needed to remain narrower.

### AI and deterministic logic have different strengths

The project demonstrated a useful division of responsibility:

```text
AI
→ interpretation of messy human input

Deterministic logic
→ trusted workflow decisions
```

### Git history is part of the project

Branches, commits, Pull Requests, reviews and documentation were used to preserve the development journey rather than only the final state.
